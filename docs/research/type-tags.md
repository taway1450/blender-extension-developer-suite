# Narrowing by a Type tag

Research for [#70](https://github.com/taway1450/blender-extension-developer-suite/issues/70) (map [#67](https://github.com/taway1450/blender-extension-developer-suite/issues/67)). Question: how ty-blender narrows by a **Type tag**, in both forms. The value form is `md.type == 'SUBSURF'` → `md: SubsurfModifier`. The sibling form is `ob.type == 'MESH'` → `ob.data: Mesh`. The settled decision is that both forms are built from one generated table.

Sources: Blender `main` at `.cache/blender-src/main` (RNA in `source/blender/makesrna/intern`), Blender's own stubs at `.cache/bpy-stubs-builtin/main`, the ty fork at `ty-blender/ruff-blender` (paths below are relative to its `crates/`), and the analysis outputs in `.cache/analysis/`.

## Answer in short

- **Where the tables come from:** RNA does not hold them. Each `refine` function is C code. `rna_Modifier_refine` returns `ModifierTypeInfo::srna` (`rna_modifier.cc:906`). `rna_ConstraintType_refine` (`rna_constraint.cc:341`) and `rna_Strip_refine` (`rna_sequencer.cc:1107`) are switch statements. `rna_Object_data_typef` is also a switch (`rna_object.cc:591`). Introspection cannot read any of them. **They must be generated by a runtime probe inside Blender at stub time**: create one instance of each tag value and read `type(x).bl_rna.identifier`. Nodes and sockets are the exception, because for built-in types `bl_idname` equals the RNA struct identifier.
- **Where the tables live:** in the **stubs**, written as ordinary class declarations, not as a table baked into the ty binary. The tables differ between Blender versions, and `ty_blender` only holds facts that do not depend on the version.
  - In the value form, each refined subclass declares its tag as a `Literal`, for example `class SubsurfModifier(Modifier): type: Literal['SUBSURF']`.
  - In the sibling form, the generator emits one private **tag view** class per tag value, for example `class _Object_MESH(Object): type: Literal['MESH']; data: Mesh`.
  - ty-blender reads one table, (base class, tag attribute, literal) → class, from the class bodies in `bpy.types`. A salsa-tracked function builds it once per stub file.
- **Mechanism:** both forms become one operation, an **intersection of the tested place with the table's class**. That is the same constraint `isinstance` produces: `NarrowingConstraint::intersection`, `narrow.rs:1132`.
  - `md` becomes `SubsurfModifier`.
  - `ob` becomes `_Object_MESH`, so `ob.data` resolves to `Mesh` through ordinary member lookup.
  - `!=` and `else` intersect with the negation, `in {...}` with a union, and `not in` with the negated members.
- **Hook sites**, three one-line hooks plus one deferred:
  1. `narrow.rs` `narrow_nominal_attribute` (`:5398`): at its top, call `blender::narrow_type_tag(...)` and return its result when it gives one. This covers `==`, `!=`, `is` and `is not`.
  2. `narrow.rs` `evaluate_expr_compare` (`:4266`): widen the attribute block's operator match to include `In` / `NotIn`, so the same hook sees membership tests.
  3. `ty_python_core/src/place.rs` `expr_compare` (`:700`): add `In | NotIn` to `can_narrow_tagged_union_base`. Without it the base place (`md`) is never recorded as possibly narrowed by an `in` test.
  4. `match md.type:` (deferred): it needs a hook in `evaluate_match_pattern_value` (`narrow.rs:4985`) and in the place builder's `pattern()`. Blender's code has only 10 such statements.

  The logic lives in a new `ty_python_semantic/src/types/dedicated/blender/type_tags.rs`.
- **Rejected alternatives:**
  - Narrowing the place `ob.data` directly fails. ty decides which places a predicate may narrow when it records the predicate (`builder.rs:2351` → `place.rs:681`), and it only considers places already in the place table. `ob.data` usually first appears *after* the `if`, so the constraint is never attached to it.
  - A closed union type (`Modifier` → `SubsurfModifier | ...`) would let upstream's `narrow_nominal_attribute` work with no hook. It fails for user-annotated `md: Modifier`, it is wrong for the user-subclassable `Node` and `NodeSocket`, and hover would show 80-member unions.

## 1. Where the tables come from

### RNA has no type → subclass table

| Type tag | Refine source | Form of the mapping |
|---|---|---|
| `Modifier.type` | `rna_modifier.cc:906` `rna_Modifier_refine` | `BKE_modifier_get_info(md->type)->srna`, a C function table |
| `Constraint.type` | `rna_constraint.cc:341` `rna_ConstraintType_refine` | `switch` |
| `Strip.type` | `rna_sequencer.cc:1107` `rna_Strip_refine` | `switch` |
| `Light.type` | `rna_light.cc:46` `rna_Light_refine` | `switch` |
| `NodeSocket` | `rna_node_socket.cc:248` | `sock->typeinfo->ext_socket.srna` |
| `Node` | `rna_nodetree.cc:1447` `rna_Node_refine` | node typeinfo |
| `Object.data` by `Object.type` | `rna_object.cc:591` `rna_Object_data_typef` | `switch` |
| `Curve` by owner object type | `rna_curve.cc:249` `rna_Curve_refine` | `FONT` → `TextCurve`, `SURFACE` → `SurfaceCurve` |
| also: `ActionStrip`, `Texture`, `Space`, `ShaderFx`, `FModifier`, `StripModifier`, `Attribute`, `LightProbe`, ... | `grep "_refine(" makesrna/intern/*.cc` | 40 refine functions |

None of these mappings can be read through `bl_rna` introspection. The stubs show the consequence: `Modifier.type` is the alias `rna_enum_object_modifier_type_items`, and `SubsurfModifier` does not redeclare `type` (`bpy/types/__init__.pyi:1022`, `:27711`). Parsing the C `switch` statements was rejected as brittle: the modifier table is not even a `switch`.

### Runtime probe in the stub generator

Blender's generator (`doc/python_api/sphinx_stub_gen.py`) already runs inside Blender, so it can build each table by instantiating every tag value:

- **Modifiers:** `ob.modifiers.new(name, type)` on a mesh object, and on a Grease Pencil object for the `GREASE_PENCIL_*` values. Then read `type(md).bl_rna.identifier`.
- **Constraints:** `ob.constraints.new(type)`. **Lights:** `bpy.data.lights.new(name, type)`. **Strips:** `sequence_editor.strips.new_effect(...)` and the other `new_*` calls.
- **`Object.type` → data:** `bpy.data.objects.new(name, data)` for each data-block type. The view class must use the refined type: `FONT` → `TextCurve`, `SURFACE` → `SurfaceCurve`, because `Curve` is refined again.
- **`FluidModifier.fluid_type` → `domain_settings` / `flow_settings` / `effector_settings`:** set `fluid_type` and see which pointer is non-None. The other two stay `None`.
- **Nodes and sockets:** no probe is needed. For a built-in class, `bl_idname` is the RNA identifier, so `ShaderNodeMath.bl_idname: Literal['ShaderNodeMath']`. `NodeSocket.type` is many-to-one (`'VALUE'` → `NodeSocketFloat`, `NodeSocketFloatFactor`, ...). It needs no special case, because the table maps one literal to the union of every class that declares it.

These are small, separately upstreamable commits to the Blender fork's generator, which is where map #67 puts stub changes. fake-bpy-module needs the same declarations, or it becomes a named exception.

### Format in the stubs

```python
class Modifier(bpy_struct):
    type: rna_enum_object_modifier_type_items = ...
class SubsurfModifier(Modifier):
    type: Literal['SUBSURF'] = ...          # value form: the tag on the refined subclass

class Object(ID):
    type: rna_enum_object_type_items = ...
    data: ID | None = ...
class _Object_MESH(Object):                 # sibling form: a private tag view
    type: Literal['MESH'] = ...
    data: Mesh = ...                        # also non-None: an object of type MESH always has data
```

The tags are true at runtime: an RNA `type` is read-only and fixed for the refined struct. The narrower override of a mutable attribute is never checked, because ty does not report diagnostics inside stubs. The table that `type_tags.rs` builds is: for every class `C` in `bpy.types` whose body declares a `Literal` for an attribute that an ancestor `B` declares with a wider type, add (B, attribute, literal) → C. Every ancestor is covered, so `CrossStrip` registers under `Strip` even through intermediate effect classes.

## 2. Mechanism in ty

### What upstream already does

- `evaluate_expr_compare` (`narrow.rs:4006`) narrows the compared place itself, so `md.type` becomes `Literal['SUBSURF']`, at `:4479`. It also calls `narrow_nominal_attribute` (`:4266`–`:4299`) for `x.attr ==/!=/is/is not y`.
- `narrow_nominal_attribute` (`:5398`) only works when the base is a **union** (`let Type::Union(union) = ... else { return None }`). It filters the union's members by their attribute type. A declared `Modifier` is not a union, so nothing happens. This is the gap behind the `narrow:*` buckets.
- `in` / `not in` never narrow the base. The attribute block only matches `Eq | NotEq | Is | IsNot`, and so does `can_narrow_tagged_union_base` (`ty_python_core/src/place.rs:700`).
- Member places (`ob.data`, `context.object.data`) are registered on every load (`ty_python_core/src/builder.rs:3484`–`:3547`). The places a predicate may narrow are computed when it is recorded, from the place table as it stands then (`builder.rs:2351`, `place.rs:629`–`:689`). A test can therefore narrow `ob` and `ob.type`, but not an `ob.data` that first appears later in the body.

### The hook

`blender::narrow_type_tag(db, env, value_ty, value_expr, attr, rhs_ty, op, is_positive)` does the following:

1. It returns `None` unless `value_ty` (or each element, for a union or an intersection) is a `bpy.types` class that has table entries for `attr`. Everything that is not Blender keeps upstream's path.
2. It reads the string literal or literals on the right-hand side: one for `==` / `is`, a tuple, set or list literal for `in`. That literal is already computed at `:4411` through `inline_membership_rhs_type`.
3. It looks up the classes and builds the constraint. A positive test gives `NarrowingConstraint::intersection(C1 | C2 ...)`. A negative test gives an intersection with `~C1 & ~C2 ...`, which is sound only when the tag is one-to-one. A literal with no entry, such as a Node's legacy `type`, gives no constraint.
4. It returns `(place of value_expr, constraint)`. Upstream's `insert_narrowing_constraint` then merges it with the other constraints.

`Object & _Object_MESH` simplifies to `_Object_MESH`, so `ob.data` reads `Mesh` and `ob.type` reads `Literal['MESH']` with no member-lookup hook. The sibling form costs nothing beyond the stub classes.

## 3. Cases that need care

| Case | Behaviour with this design |
|---|---|
| `ob.data` read again after a call | Works. ty does not invalidate narrowing on calls; rebinding `ob` drops it. |
| `for md in ob.modifiers: if md.type == 'X':` | Works. Each iteration rebinds `md` and the test narrows that binding. |
| `if md.type in {'A', 'B'}:` | Works with hook sites 2 and 3, giving a union of the two classes. |
| `elif` / `else` after `==` | Negative intersection. Correct for one-to-one tags. For many-to-one tags (sockets), the negation removes every class with that tag, which is still correct. |
| `match md.type: case 'SUBSURF':` | Not covered by hook sites 1–3. Needs site 4. Only 10 occurrences in `scripts/` and Cycles. |
| `data = ob.data` before the test | Not narrowed: `data` is a separate binding. This is accepted. |
| `ob = context.object; if ob.type == ...` | Needs `context.object` to be non-None first: the Context ticket. `ob.type` on `Object \| None` already errors. |
| Test in `poll()`, use in `draw()` | Not reachable by narrowing. Most of the 294 `DomainSettings \| None` diagnostics in `properties_physics_fluid.py` are of this kind. Seven `draw` methods re-test `md.fluid_type == 'DOMAIN'` and are covered. The rest belong to the open `poll()` narrowing item. |
| Custom `Node` / `NodeSocket` subclasses | The table only holds stub classes. An add-on's `bl_idname = 'MyNode'` is not in the table, so it is not narrowed (there is no regression). Adding them from the Add-on index is possible later. |
| Single-value tags (`ActionStrip.type: Literal['KEYFRAME']`) | The 56 `ActionStrip` diagnostics come from code that never tests the tag. That is a stub fact (`strips` items are `ActionKeyframeStrip`), which belongs to `api_types`, not narrowing. |

## 4. How much of the ~1,540 this reaches

From `.cache/analysis/buckets-builtin.txt` and `main-builtin.txt`:

- `narrow:base-class-needs-subtype` (482): `Constraint` 81, `Strip` 109, `ActionStrip` 56, `Node` 58, `NodeSocket` 53, `Light` 42, `Curve` 33, `Modifier` 26, `Texture` 12, `Space` 13. Narrowing reaches the share whose code tests the tag in the same function. `ActionStrip` is a stub fact, and `Space` belongs to `context_members`.
- `narrow:Object.data-by-type` (346): mostly reached by the sibling form. Some hits are `ID` from `object.evaluated_get()`, which is a stub return type and not a tag.
- `nullable:type-discriminated-pointer` (716): **mostly not Type tags.**
  - `SceneEEVEE` (101) is an embedded pointer, covered by the Pointers decision.
  - `RigidBody*` (115), `FieldSettings` (57) and `Brush*Settings` (121) are optional pointers or ID pointers.
  - Only Fluid (`Domain/Flow/EffectorSettings`, 342) is sibling-tagged, and most of it is gated by `poll()`.
- The tag tests in Blender's shipped Python: `.type ==/!=` 808, `.type in/not in` 90, `bl_idname` comparisons 79, `match ... .type` 10, `fluid_type` tests 8.

The bucket names overstate how much Type tags fix. The spec should expect the `narrow:*` buckets to shrink substantially and `type-discriminated-pointer` to shrink only by its Fluid share.
