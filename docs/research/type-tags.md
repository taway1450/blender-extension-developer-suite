# Narrowing by a Type tag

Research note, 2026-11-06, for [#70](https://github.com/taway1450/blender-extension-developer-suite/issues/70) (map [#67](https://github.com/taway1450/blender-extension-developer-suite/issues/67)). Trimmed on 2026-11-18 to the rationale and the Blender/ty facts; the build plan and counts were dropped; the issue keeps a summary of the findings.

Question: how ty-blender narrows by a **Type tag**, in both forms. The value form is `md.type == 'SUBSURF'` → `md: SubsurfModifier`. The sibling form is `ob.type == 'MESH'` → `ob.data: Mesh`. Both forms are built from one generated table.

Sources: Blender `main` at `.cache/blender-src/main` (the map's `dc491af090`; RNA in `source/blender/makesrna/intern`) and the ty fork at `ty-blender/ruff-blender` (paths below are relative to its `crates/`).

Main now: `match` on a tag and constructor narrowing (`ob.constraints.new('COPY_LOCATION')` → `CopyLocationConstraint`) are supported too; see `tests/typecheck/features/type_narrowing/README.md`. The tags are written into the stubs by the Blender fork's `sphinx_doc_gen_type_tags.py`; see [type-tag-data-sources.md](type-tag-data-sources.md).

## 1. Where the tables come from and where they live

**RNA does not hold them.** Each `refine` function is C code, and introspection cannot read any of them:

| Type tag | Refine source | Form of the mapping |
|---|---|---|
| `Modifier.type` | `rna_modifier.cc:906` `rna_Modifier_refine` | `BKE_modifier_get_info(md->type)->srna`, a C function table |
| `Constraint.type` | `rna_constraint.cc:341` `rna_ConstraintType_refine` | `switch` |
| `Strip.type` | `rna_sequencer.cc:1107` `rna_Strip_refine` | `switch` |
| `Light.type` | `rna_light.cc:46` `rna_Light_refine` | `switch` |
| `NodeSocket` | `rna_node_socket.cc:248` | `sock->typeinfo->ext_socket.srna` |
| `Node` | `rna_nodetree.cc:1447` `rna_Node_refine` | node typeinfo |
| `Object.data` by `Object.type` | `rna_object.cc:591` `rna_Object_data_typef` | `switch` |
| `Curve` by owner object type | `rna_curve.cc:249` `rna_Curve_refine` | `FONT` → `TextCurve`, `SURFACE` → `SurfaceCurve` |
| also: `ActionStrip`, `Texture`, `Space`, `ShaderFx`, `FModifier`, `StripModifier`, `Attribute`, `LightProbe`, ... | `grep "_refine(" makesrna/intern/*.cc` | |

So the tables are generated by a runtime probe inside Blender at stub time: create one instance of each tag value and read `type(x).bl_rna.identifier`. Nodes and sockets are the exception, because for built-in types `bl_idname` equals the RNA struct identifier.

**The tables live in the stubs**, written as ordinary class declarations, not as a table baked into the ty binary. The tables differ between Blender versions, and `ty_blender` only holds facts that do not depend on the version.

- In the value form, each refined subclass declares its tag as a `Literal`, for example `class SubsurfModifier(Modifier): type: Literal['SUBSURF']`.
- In the sibling form, the generator emits one private **tag view** class per tag value, for example `class _Object_MESH(Object): type: Literal['MESH']; data: Mesh`.

The tags are true at runtime: an RNA `type` is read-only and fixed for the refined struct. The narrower override of a mutable attribute is never checked, because ty does not report diagnostics inside stubs.

Both forms become one operation, an intersection of the tested place with the table's class, the same constraint `isinstance` produces. `Object & _Object_MESH` simplifies to `_Object_MESH`, so `ob.data` reads `Mesh` through ordinary member lookup, with no member-lookup hook.

## 2. Rejected alternatives

- **Narrowing the place `ob.data` directly.** ty decides which places a predicate may narrow when it records the predicate (`ty_python_core/src/builder.rs` → `place.rs`), and it only considers places already in the place table as it stands then. `ob.data` usually first appears *after* the `if`, so the constraint is never attached to it. A test can therefore narrow `ob` and `ob.type`, but not an `ob.data` that first appears later in the body. Narrowing `ob` to a tag view sidesteps this.
- **A closed union type** (`Modifier` → `SubsurfModifier | ...`) would let upstream's `narrow_nominal_attribute` work with no hook (it only filters a base that is already a union). It fails for user-annotated `md: Modifier`, it is wrong for the user-subclassable `Node` and `NodeSocket`, and hover would show 80-member unions.
- **Parsing the C `switch` statements** was rejected as brittle: the modifier table is not even a `switch`.
