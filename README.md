# blender-extension-developer-suite
A suite of tools for developing Blender extensions.

## Tasks

The tooling runs as [mise](https://mise.jdx.dev) tasks (`mise tasks` lists them, `mise run <task> --help`
shows the options). They need `uv`, `git` and, for building ty, `cargo`. Everything they produce is
cached under `.cache/`.

| Task | What it does |
| --- | --- |
| `mise run ty:build [--profile dev|profiling|release]` | Build ty from the `ty-blender` submodule. `dev` (the default) is incremental and rebuilds in well under a minute; `profiling` has release optimisations without LTO (fast binary, rebuilds take minutes); `release` is what ty ships, with fat LTO. |
| `mise run ty:restore [--release <tag>] [--force]` | Download ty's dev build (`target/debug`, with rustc's incremental data) that CI publishes for every `ty-blender` bump (`.github/workflows/ty-cache.yml`), so the next `ty:build` is a no-op instead of a 9-minute cold build, or an incremental one for what differs from the cache's `ruff-blender` commit. The sources that match that commit get an old timestamp, the rest the current one. CI keeps the newest few builds as releases `ty-cache-<date>-<commit>`; the release `ty-cache` points at the newest, and `--release <tag>` restores an older one. Linux, at this repo's path in the cloud image (`/home/user/blender-extension-developer-suite`), with `zstd`. |
| `mise run ty:cache-pack` | Build ty from a clean `ruff-blender` checkout, with every source set to an old timestamp first, and pack `target/debug` into `.cache/ty-cache/` (archive plus `manifest.json`) for `ty:restore`; CI runs it. |
| `mise run ty:test [--mdtest <path>]` | Run ty-blender's upstream Rust tests and mdtests (`ty_python_semantic`, `ty_blender`) with the dev build, without updating snapshots: a regression check for a change to the fork, whose Blender support is tested by the feature tests here. |
| `mise run ty:generate` | Run `cargo dev generate-all` in `ty-blender/ruff-blender` (dev profile): rewrites the rule reference (`crates/ty/docs/rules.md`), `ty.schema.json` and the other generated docs, which ruff-blender asks for after a change to its lint rules or options. Commit what it changes there. |
| `mise run ruff:build [--profile ...]` | Build ruff from the `ty-blender` submodule, in the same cargo `target/` as ty. Only to test a change to ruff itself: the fork changes no ruff crate, so the `lint:*` / `format:*` tasks run stock ruff. |
| `mise run blender:download <version>` | Download the official Blender release into `.cache/blender-bin/<version>` (URLs and checksums from `fake-bpy-module/src/versions.yml`). |
| `mise run blender:build <name> [--ref <ref>] [--update]` | Build Blender from source: a worktree of the `blender` submodule at `<ref>` (default `<name>`, e.g. `main`) in `.cache/blender-src/<name>`, CMake/Ninja build in `.cache/blender-build/<name>`, installed into `.cache/blender-bin/<name>` like a download. The precompiled libraries are shared by all builds in `.cache/blender-libs/`. `--update` fetches the ref again and rebuilds incrementally, and so does an uncommitted edit in the worktree; `--config lite` builds faster; `--ccache` compiles through ccache. A build is reused while its source (commit and uncommitted changes), preset, build type and configure arguments (recorded in `.build-info`) are unchanged. |
| `mise run blender:restore <name> [--release <tag>] [--ccache-only] [--force]` | Download the Blender build cache that CI publishes (`.github/workflows/blender-cache.yml`): the build directory, install and ccache of `<name>`. CI keeps the newest few builds as releases `blender-cache-<name>-<date>-<commit>`; the release `blender-cache-<name>` points at the newest, and `--release <tag>` restores an older one. The sources and libraries that match the cache's commits get an old timestamp, so the next `blender:build <name> --ccache` rebuilds only what differs (a one-file edit takes under half a minute instead of two hours). Linux, at this repo's path in the cloud image (`/home/user/blender-extension-developer-suite`), with `gcc-14`, `zstd` and ccache in `/usr/local/bin`; `--ccache-only` works anywhere but replays every compile (about 4 minutes). |
| `mise run blender:cache-pack <name>` | Pack a clean `blender:build` into `.cache/blender-cache/<name>/` (archives plus `manifest.json`) for `blender:restore`; CI runs it. |
| `mise run stubs:generate <version>` | Generate bpy stubs with `fake-bpy-module` into `.cache/bpy-stubs/<version>` and with Blender's own stub generator (`doc/python_api/sphinx_stub_gen.py`, Blender 5.2 and later) into `.cache/bpy-stubs-builtin/<version>`, using a worktree of the `blender` submodule and the downloaded Blender binary. Both work from the rst API docs Blender generates, cached in `.cache/bpy-rst/<version>`. `--generator runtime` (not part of the default `all`) runs the fork's `doc/python_api/runtime_stub_gen.py` instead: Blender writes and parses its own rst with its factory add-ons disabled, re-exports the startup classes from their modules and copies the Python source of its script folders, into `.cache/bpy-stubs-runtime/<version>`, regenerated also on edits under `doc/python_api` or to `_rna_info.py` (`docs/research/runtime-stub-generator.md` §7); every `check:*` task takes the same `--generator`. The rst docs and the stubs are regenerated when the Blender worktree moves to another commit or the Blender binary is another build (a rebuild with other configure options, another release download), and the stubs also when their generator changes: a new `fake-bpy-module` submodule commit or uncommitted edits to its `src/`, or edits to `sphinx_stub_gen.py` in the worktree (`--force` regenerates them anyway). |
| `mise run check:blender <version> [--update]` | Type-check the Blender source of that version with ty, with the bundled packages Blender's code imports (numpy, setuptools, requests, ...) on the search path (linked from `.cache/blender-site/<version>/`), the directories Blender's tools and tests add to `sys.path` themselves, and the modules nothing can resolve (compiled into Blender, GDB's, developer-tool requirements) allowed unresolved; the full output goes to `.cache/ty-results/<version>.txt` (`<version>-builtin.txt` with Blender's own stubs). `lib/`, `extern/` and the dead 2.7x test scripts (`tests/python/view_layer/`, `bl_mesh_modifiers.py`, `rna_array.py`) are left out. Each diagnostic is sorted into a cause, whose group says where the fix belongs (`blender-fix`, `assumption`, `implied-narrowing`, `imprecise-annotation`, `typechecker-fix`, `typing-debt`, `unsorted`), and an area (`scripts/_buckets.py`); the cause × area table with each cause's group and slice, the totals per group, the error and warning totals and the counts per rule and severity go to `.cache/ty-results/<version>-<generator>-summary.txt`, samples per cause to `...-buckets.txt`. For `main` the summary is compared with `tests/blender/expected/<generator>/main-summary.txt`: a difference is printed but doesn't fail the task, and `--update` records it. |
| `mise run check:stubs <version>` | Type-check the generated bpy stubs themselves with ty; the full output goes to `.cache/ty-results/stubs-<version>.txt` (`stubs-<version>-builtin.txt` for Blender's own stubs). |
| `mise run check:addons <version> [addon...]` | Type-check the example addons in `examples/addons/` with ty against the bpy stubs. |
| `mise run check:features <version> [feature...] [--update]` | Type-check the feature tests in `tests/typecheck/features/` (`assert_type` and expected-error markers) with ty-blender and compare with `tests/typecheck/expected/<generator>/<version>.txt`; fails when the results change. A summary per feature goes to `.cache/typecheck-results/<version>/<generator>/summary.md`. See [tests/typecheck/README.md](tests/typecheck/README.md). |
| `mise run check:ide <version> [feature...] [--update]` | Query ty's language server at the `^hover` / `^signature` / `^completion` / `^deprecated` markers in `tests/typecheck/` and compare with `tests/typecheck/expected/<generator>/<version>.ide.md`; fails when the results change. |
| `mise run check:oracle <version> [feature...]` | Run stock ty on each feature-test add-on with its reference stubs (`_expected/` deltas merged into the bpy stubs of both generators) and check that every marker holds; a disagreement means the hand-written expectations are inconsistent. Summary in `.cache/typecheck-results/<version>/<generator>/oracle.md`. |
| `mise run check:load <version> [feature...]` | Import, register and unregister every feature-test add-on in Blender and compare with its `_expected/runtime.toml`: add-ons that fail on purpose say so and with which error, and probes check what an add-on does at runtime after register. |
| `mise run features:generate [--check]` | Write the generated feature-test add-ons (`tests/typecheck/features/*/generated/`, from `scripts/feature_generators/`) and the import roots in `tests/typecheck/ty.toml`; `--check` fails if they are out of date. |
| `mise run lint:blender <version>`, `lint:stubs`, `lint:addons [addon...]`, `lint:features [feature...]` | Lint the Blender source (without `lib/` and `extern/`), the generated bpy stubs (once per stub generator), the example add-ons or the feature-test add-ons with stock ruff (`uvx ruff@<version ruff-blender is based on>`, or `--ruff <path>`), twice: with stock settings (`--isolated`) and with the profile in `config/ruff/` (`blender.toml`, `stubs.toml`, `addons.toml`, `features.toml`). The counts per rule of both runs are printed side by side; the full output goes to `.cache/ruff-results/lint-<target>-<version>[-builtin]-{default,profile}.txt`. `lint:addons` fails when the profile run has findings. |
| `mise run format:blender <version>`, `format:stubs`, `format:addons`, `format:features` | The same targets and configurations with `ruff format --check --diff`, which never writes files; the diffs go to `.cache/ruff-results/format-…`. |
| `mise run lint:scripts` | Lint (with fixes) and format the tooling in `scripts/` with the pinned upstream ruff through [prek](https://github.com/j178/prek) (`.pre-commit-config.yaml`, settings in `scripts/ruff.toml`). `uvx prek@0.5.6 install` runs the hooks on every commit. |
| `mise run probe:freestyle <version>` | Render the factory-startup scene with Freestyle in background Blender (Cycles, small size): a style module using `pyShuffleBP1D` and `pyRandomColorShader` renders twice, and a parameter-editor line set with the noise and stroke-normal modifiers once. Fails when a render or style module raises, the module draws no strokes, the seeded colours differ between the renders or `random.seed` is no longer callable; Blender's output and the results go to `.cache/freestyle-probe/<version>/`. |
| `mise run probe:gltf-rigify <version> [--only gltf\|rigify]` | Run Blender's own glTF import, export and round-trip tests (`tests/python/io_gltf_*_test.py` against `tests/files/io_tests/gltf/` of the source worktree) and generate a Rigify rig with `bpy.ops.pose.rigify_generate()` from every metarig, the human metarig with its face upgraded to the skin rigs, and every rig type's sample, in background Blender. Fails when a glTF test fails or a rig raises or generates nothing; Blender's output and the results go to `.cache/gltf-rigify-probe/<version>/`. |
| `mise run probe:modifiers-new <version>` | Check in background Blender that the shipped callers of `modifiers.new()` handle a modifier the object rejects (it returns None): an empty rejects `SUBSURF`; each quick-effects operator (Fur, Explode, Smoke, Liquid) finishes and adds its modifiers on the default cube, and returns `{'CANCELLED'}` with an error report when its objects reject the modifier (emulated by a stand-in object, since the operators only take meshes), Fur, Smoke and Liquid leaving the scene as it was, also when only a second selected object rejects it; the Python FBX importer adds the armature and subdivision modifiers (files from `tests/files/io_tests/fbx/` of the source worktree). Fails when a check raises or does not hold; Blender's output and the results go to `.cache/modifiers-new-probe/<version>/`. |
| `mise run probe:node-menus <version>` | Draw every node-add and node-swap menu `bl_ui` registers (each `generate_menu` class, the texture templates included) by calling its `draw` on a recording stub layout in a stand-in node editor, once per tree variant the menus read (geometry modifier / tool, shader object / light / world / line style under EEVEE and Cycles, compositor scene / sequencer, texture), in background Blender. Fails when a draw raises or uses an unknown operator, operator property or menu, or a menu's `poll` rejects every variant, and lists the draws whose entries changed since the previous run; the results go to `.cache/node-menu-probe/<version>/`. |
| `mise run probe:ui-draw <version>` | Draw the panels and menus the spec #146 review found raising in a rare state, in that state, in background Blender: each `draw` runs on a stub layout that rejects a None RNA pointer as Blender's `UILayout` does, with a context in the state (a paint mode whose brush was deleted, for its panels and its tool header settings, a Properties editor pinned to particle settings, object data or an armature, a node group interface without an active item, a workspace without a sequencer scene, a sequencer scene without a sequence editor, no open project). With the glTF add-on enabled, it also draws the exporter's action filter list after an action is deleted and runs the material variant operators on a curve, and it renders with Freestyle (Cycles, small size) while the scene camera is an empty. Fails when a draw, operator or render raises or a poll rejects its state; Blender's output and the results go to `.cache/ui-draw-probe/<version>/`. |
| `mise run probe:runtime-stubs <version> [--addon <path> ...]` | Compare the `runtime` stubs of `stubs:generate` with the builtin and fake-bpy-module stubs of the version (modules, classes and members each has alone, and the members typed differently), list what the factory add-ons register, and run the runtime generator's add-on mode on each add-on (default: the example add-ons): the delta enabling it makes, a merged package with its registrations and an overlay stub per `.blend` under it. Needs the builtin and fake-bpy-module stubs; everything goes to `.cache/runtime-stubs/<version>/` (`summary.md`). |
| `mise run probe:blend-typing <version> [--make] [--update-overlays]` | Run the four .blend typing prototypes of `docs/research/blend-file-typing.md` §8 on the example add-ons in `prototypes/blend_typing/examples/`, for each file an add-on binds in its `[tool.blender] blend-files`: B reads it without Blender, G opens it in background Blender (the loaded state), C writes an overlay from each manifest (`--update-overlays` writes B's into the add-on's committed `_blend/<file>.pyi`), and A types the add-on's `reveal_type` calls from the files directly. `--make` first rebuilds the generated example files in Blender. Needs the builtin stubs of the version; the outputs and `summary.md` (where B and G disagree) go to `.cache/blend-typing/<version>/`. |
| `mise run probe:never-none <version> [--limit <n>]` | Research for #109: read the RNA pointers and function returns in background Blender, in synthetic edge states built from factory startup (new data, copies, save and append, invalid arguments, every node tree and ID type, `read_homefile` / `read_factory_settings`) and in every .blend under `tests/files/` of the source worktree (`--limit` takes only the first N), and count per member and state how many reads were None. A file that crashes Blender is recorded and skipped on the next run; the table goes to `.cache/never-none-probe/<version>/table.md`. |
| `mise run report:flags <version>` | For every documented class, property, function, parameter, return value and operator argument, compare its RNA flags with the behaviour probed in Blender, the API docs and the bpy stubs; per-flag counts and wrong flag combinations go to `.cache/flag-report/<version>/summary.md`, all rows to `rows.md` / `rows.csv`. |

`<version>` is either a Blender release such as `5.2`, which is downloaded when needed, or the name of a
build made with `blender:build` (e.g. `main`), which has to be built first:

```sh
mise run blender:build main               # once; takes a while and needs several GB for libraries and build
mise run check:addons main
mise run blender:build main --update      # later: fetch main again, rebuild and (automatically) regenerate the stubs
mise run blender:build my-fix --ref my-feature-branch
```

`--blender <path>` uses any other Blender binary instead. The check tasks build ty and generate missing stubs
themselves. The ty tasks take `--profile dev|profiling|release` for that build (default `dev`, incremental), or
`--ty <path>` to use a binary that is already built; `check:oracle` and the ruff tasks build nothing:

```sh
mise run check:features main properties
mise run check:ide main properties --ty ty-blender/ruff-blender/target/debug/ty.exe
```

When results change, `check:features` and `check:ide` list each entry as `-` gone, `~` changed or `+` new, with
ty's message under a new `check:features` entry and a diff under a changed `check:ide` section, then the counts
per feature.

The stub, check and report tasks run once per stub generator: `fake-bpy-module` and, for Blender 5.2 and later,
`builtin` (Blender's own). `--generator fake-bpy-module` or `--generator builtin` picks one; the report against
Blender's own stubs goes to `.cache/flag-report/<version>/builtin/`.

Building Blender needs the tools from the [Blender build docs](https://developer.blender.org/docs/handbook/building_blender/)
and git LFS: on Windows Visual Studio 2022 or newer with the "Desktop development with C++" workload (the
task loads the Visual Studio environment itself), on macOS Xcode and on Linux the packages from
`build_files/build_environment/install_linux_packages.py`. CMake and Ninja come from PyPI. Branches that only exist on a
fork need that fork as the `origin` of the `blender` submodule (`git submodule sync blender`).
